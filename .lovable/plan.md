# TicketNest — frontend for your live-event ticketing API

A modern, purple-accented booking site matching your screenshot, wired to your TicketNest API through a base URL you can change at any time (a Settings dialog + saved value, defaulting to `http://localhost:8080`). Everything your API supports is live; the parts your API does not have yet (seats-in-a-show, cart, payment, bookings) are built as working UI on top of the seat data you do expose, ready to switch to real endpoints later.

## What gets built

**Public browsing**
- Home: hero ("Book Events, Create Memories"), popular shows row, city/genre quick filters.
- Shows list: search, city / genre / date-range filters, sorting, pagination — all mapped to `GET /api/shows` filter + pageable params.
- Show detail: poster block, title, genre, venue with address, start time, seat tiers, and an order summary card with "Select Seats".
- Venues: list of venues and a venue page with its seat tiers.

**Accounts**
- Register, login, logout against `/auth/*`; access + refresh tokens stored client-side with automatic refresh on 401 and retry of the failed request.
- Profile page showing name, email, phone, roles (read-only fields where the API has no update endpoint, clearly marked).
- Header reflects signed-in state with an account menu and sign out.

**Seat selection & booking (UI flow)**
- Seat map built from `GET /api/venues/{id}/seats`, grouped by row, colour-coded by tier, with available / selected states.
- Selection summary, cart, checkout (contact details → payment method → review), and a confirmation screen with a booking reference.
- Bookings and tickets are kept in the browser only, since there are no booking/order endpoints yet. Each screen is labelled as pending backend so nothing looks falsely real, and the money/booking steps are isolated in one place to swap out later.

**Admin console** (shown to users whose roles carry the matching permissions)
- Venues: create, edit, delete, plus batch seat creation by row ranges and tier.
- Shows: create, edit, delete with venue picker, genre, start time, status.
- Roles: list, create, edit, delete, with permission checkboxes from `GET /api/admin/permissions`.
- Users: paginated list with role reassignment.

## Design

Follows the screenshot: light neutral background, white cards, purple primary, dark hero band, sidebar layout for account/admin areas, star ratings and price accents, rupee formatting. Responsive down to mobile. All colours/typography defined as design tokens, no hardcoded values.

## Technical notes

- Typed API client generated by hand from your OpenAPI document (`src/lib/api/*`): one fetch wrapper handling base URL, bearer token, refresh-and-retry, and error normalisation; one module per controller.
- Base URL resolution order: saved user setting → `VITE_API_BASE_URL` → `http://localhost:8080`. Calls run in the browser, so your Spring app needs CORS to allow the preview origin; the connection dialog states this and surfaces a clear "cannot reach API" banner when requests fail.
- TanStack Router routes: `/`, `/shows`, `/shows/$id`, `/venues`, `/venues/$id`, `/auth/login`, `/auth/register`, `/checkout`, `/confirmation/$ref`, `/account/*` (profile, bookings, tickets), `/admin/*` (venues, venue seats, shows, roles, users). Admin and account routes sit behind a pathless auth gate.
- Server data via TanStack Query with keys per filter/page; mutations invalidate their lists.
- Each page gets its own title/description/social metadata.
- Pagination and filter state live in the URL so views are shareable.
- No database or backend is added on this side — your API stays the single source of truth.
